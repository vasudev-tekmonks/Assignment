## 3. Stream-Based File Processing

### Implementation

- The application uses `fs.createReadStream()` to read `input.txt` in chunks rather than loading the entire file into memory.
- The `data` event is triggered when a chunk of data is available.
- Each chunk is converted into a string and transformed to uppercase using `toUpperCase()`.
- The transformed chunk is written to `output.txt` using `fs.createWriteStream()`.
- This process continues until all input data has been read.

### Stream Events

- **`data`** — Receives a chunk of input data.
- **`end`** — Indicates that the readable stream has finished reading the input.
- **`finish`** — Indicates that the writable stream has finished writing all data supplied to it.
- **`error`** — Handles errors occurring during reading or writing.
- **`drain`** — Indicates that the writable stream's internal buffer has drained sufficiently for writing to resume.

### Error Handling

- The readable stream's `error` event reports problems such as a missing or inaccessible input file.
- The writable stream's `error` event reports problems encountered while writing the output.
- When a stream fails, the other stream is destroyed to stop unnecessary processing.

### Backpressure Handling

- If `write()` returns `true`, the producer can continue writing.
- If `write()` returns `false`, the writable stream's buffer has reached its backpressure threshold. The chunk has still been accepted, but the producer should slow down.
- The application pauses the readable stream when `write()` returns `false`.
- The readable stream resumes when the writable stream emits `drain`.

Backpressure prevents the readable stream from producing data faster than the writable stream can handle it, helping control memory usage.

## 4. Blocking vs. Non-Blocking Operations

### Blocking Operations

## Comparison

| Blocking | Non-Blocking |
|---|---|
| Prevents the JavaScript thread from progressing until the synchronous operation returns. | Allows the JavaScript thread to perform other work while I/O is pending. |
| Can delay the handling of other requests. | Helps maintain server responsiveness. |
| Example: `fs.readFileSync()` | Examples: `fs.readFile()` and `fs.createReadStream()` |

**Note:** Non-blocking I/O does not mean that JavaScript callbacks execute simultaneously on the same thread. The event loop coordinates callbacks, while Node.js and its underlying system facilities handle asynchronous operations.

## 5. Node.js Clustering

### Purpose

- By default, a Node.js application runs JavaScript on one main thread within a single process.
- The Cluster module allows an application to create multiple worker processes.
- Each worker is a separate Node.js process with its own JavaScript execution environment.

### Implementation

- The primary process creates workers using `cluster.fork()`.
- Each worker creates an HTTP server listening on port `8080`.
- The HTTP response includes the worker ID that handled the request.
- The primary process listens for the Cluster module's `exit` event.
- When a worker exits, the primary process logs the worker ID, process ID, exit code, and signal.
- The primary process forks a replacement worker.

### Primary Process vs. Worker Process

- **Primary process:** Creates and monitors workers, handles worker exits, and starts replacements.
- **Worker process:** Runs the HTTP server and responds to incoming requests.
- **Worker ID:** Identifies a worker within the cluster.
- **Process ID (PID):** Identifies the operating-system process.

## 6. How to Run the Application

### Run the File Processor

1. Ensure `input.txt` contains text to process.
2. Run:

   ```bash
   node fileProcessor.js
   ```

3. Wait for the success message:

   ```text
   File written successfully.
   ```

4. Open `output.txt`.
5. Verify that its contents match `input.txt`, with alphabetic characters converted to uppercase.
6. Confirm that the output contains the complete input content and is not truncated.

### Run the Clustered HTTP Server

1. Open a terminal in the project directory.
2. Start the server:

   ```bash
   node clusterServer.js
   ```

3. Observe the primary process logs showing worker creation and worker process IDs.
4. Wait for the workers to report that the server is listening on port `8080`.
5. Keep this terminal running while testing requests.

## 7. Testing Guide

### Test 1: Large File Processing

On Linux, compare the generated output with the expected uppercase version:

```bash
tr '[:lower:]' '[:upper:]' < input.txt | cmp - output.txt
```

- If the command produces no output and exits successfully, the files match the expected transformation.
- If it reports a difference, inspect the files for missing, extra, or incorrectly transformed content.

### Test 2: Missing Input File

- Temporarily rename `input.txt`, or move it to another location.
- Run:

  ```bash
  node fileProcessor.js
  ```

- Verify that the application logs a read error.
- Restore the original filename before continuing.

### Test 3: HTTP Request Handling

- Start the clustered server:

  ```bash
  node clusterServer.js
  ```

- Send a GET request to:

  ```text
  http://localhost:8080
  ```

- The response should contain a message similar to:

  ```text
  Request is handled by process with id: 2
  ```

- The worker ID may differ depending on which worker handles the request.

### Test 4: Multiple HTTP Requests

- Keep the server running.
- Send multiple GET requests to `http://localhost:8080`.
- Use a browser, a REST Client extension, or the following Linux shell command:

  ```bash
  for i in $(seq 1 20); do
    curl -s http://localhost:8080
    echo
  done
  ```

- Observe the worker IDs in the responses.
- Different IDs demonstrate that different workers are handling requests.
- It is possible for multiple requests to be handled by the same worker; equal distribution is not guaranteed.

### Test 5: Worker Failure and Replacement

- Start the server and identify a worker PID in the primary process logs.
- Do not terminate the primary process.
- Open a second terminal.
- Replace `<WORKER_PID>` with the actual PID of one worker, then run:

  ```bash
  kill -TERM <WORKER_PID>
  ```

- Observe the primary process terminal.
- Verify that it logs the exited worker's ID, PID, exit code, and signal.
- Verify that it forks a replacement worker and logs the replacement worker's ID and PID.
- Send another GET request to `http://localhost:8080`.
- Confirm that the server continues responding through a surviving or replacement worker.

**Important:** Terminate only a worker process. If you terminate the primary process, it cannot create replacement workers.
